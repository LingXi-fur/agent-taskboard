## 背景

main 上的 CI 在 macOS 一直失败，Linux 和 Windows 已经是绿的（最近一次：run 45332212929）。失败的都是 `tests/test_serve_observe.py` 里 `ObserveAutoSwitchTests` 的 3 个测试：

- `test_starts_in_observe_mode_outside_a_repository`
- `test_observe_flag_wins_inside_a_taskboard_repo`
- `test_git_repo_without_taskboard_falls_back_with_hint`

已有的诊断输出说明：子进程里的服务**已经启动**（stderr 打印了 observe 提示），但测试发出的每个 HTTP 请求都超时（`TimeoutError('timed out')`）。也就是说服务起来了，请求处理却卡住了。本机用空 HOME 复现不了。

## 要做的事

1. **先拿到卡住的位置，再修。** 在测试启动服务子进程时加一个环境变量（例如 `ATB_TEST_FAULTHANDLER=1`）。服务入口检测到它时调用 `faulthandler.dump_traceback_later(10, exit=False, repeat=False)`，把所有线程的调用栈打到 stderr。测试超时时把子进程 stderr 一起打印出来（现有的 stderr 报告逻辑可以复用）。这个钩子只在设置了环境变量时生效，正常运行不受影响。
2. 推到你的分支后，用 `gh run list` / `gh run view <id> --log-failed` 读 macOS 的调用栈（输出要有上限，只看相关的几十行）。
3. 根据调用栈**修根因**。常见可疑点（仅供参考，以调用栈为准）：
   - macOS 上 `localhost` 先解析成 `::1`，而服务只绑了 `127.0.0.1`（或反过来）；
   - 第一个请求里做了耗时操作（扫描 HOME 下的会话存储、`git` 子进程、`getfqdn`/反向 DNS 等）；
   - 单线程 HTTPServer 被长连接（SSE/stream）占住，后面的请求排队。
4. 修好后**保留** faulthandler 钩子（只受环境变量控制），以后再卡住可以直接看调用栈。
